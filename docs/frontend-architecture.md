# Frontend Architecture — Global Foundation

This is the day-1 scaffold for `resources/js/`, built before most business
features exist. Cross-cutting infrastructure (`shared/`, `services/`,
`types/`, etc.) is fully wired; the 16 business-domain directories under
`resources/js/modules/<domain>/` are scaffolded with the same internal
shape (tracked via `.gitkeep` per empty subfolder) but hold real code only
for `auth` so far. Matching Inertia pages nest separately under
`resources/js/pages/<domain>/` (Inertia's page resolver and the Blade root
view both hardcode `resources/js/pages/`, so existing pages can't move into
`modules/` itself — see below for how future pages reconcile this). See the
folder tree and the per-folder rules below for what goes in a module vs.
the global/shared folders.

## Why each folder exists

- **assets/** — static files that aren't run through Tailwind's `@source`
  scanning (raster images, downloadable fonts). SVGs used as components still
  live next to the component that renders them.
- **shared/components/** — reusable, presentational UI with zero business
  logic. Split by *kind of concern* (ui/forms/feedback/layout/charts), not by
  feature, so a component here never imports from a domain module.
  `ui/` is excluded from ESLint (see `.eslintrc.cjs`), matching the
  shadcn-vue convention for vendored primitives.
- **shared/composables/** — global, reusable Composition API functions with
  no domain knowledge (`useTheme`, `useToast`, `useDebounce`,
  `useLocalStorage`). A domain module gets its own `composables/` for
  business-specific ones (e.g. `useProductFilters`) — those never live here.
- **shared/lib/** — generic utility functions that aren't Vue-reactive and
  don't belong to one domain (`cn()`, a `clsx` + `tailwind-merge` class
  helper). If a future module needs a business-specific pure helper, it goes
  in that module's own `utils/`, not here.
- **shared/stores/** — Pinia stores whose state is cross-cutting UI/platform
  concerns, not business data: `theme`, `locale`. A store belongs here only
  if it's generic enough to reuse in another project, not just "used by
  more than one module" (that distinction is what separates `shared/` from
  promoting something to a global folder).
- **shared/types/** — types owned by `shared/`'s own stores/composables
  (`theme.ts`, `toast.ts`). Not a dumping ground — only types with no
  framework or business meaning outside `shared/`.
- **constants/** — cross-cutting, environment-independent values (HTTP
  status codes, localStorage key names). Business enums (order statuses,
  permissions, roles) belong inside the module that owns that concept, not
  here.
- **i18n/** — the single `vue-i18n` instance and its locale files. Feature
  modules add their own message namespaces as they're built; the instance
  itself stays global.
- **layouts/** — page-level layout shells: `AuthenticatedLayout` (dashboard,
  settings) and `GuestLayout` (auth pages). Stays global rather than moving
  into a module because more than one page domain shares each layout.
- **modules/** — one directory per business domain
  (`resources/js/modules/<domain>/`, each owning its own
  `components/composables/constants/pages/services/stores/types/utils`).
  Every module gets the identical skeleton up front (tracked via
  `.gitkeep` per empty subfolder) so the target shape is visible from day
  one, even though only `auth` has real code so far
  (`stores/auth.store.ts`, `services/auth.service.ts`, `types/auth.ts` —
  moved out of the old global `stores/`/`services/`/`types/` folders
  because they're auth-specific, not cross-cutting). A module's `pages/`
  subfolder is for future composition-root files only — existing Breeze
  pages stay in `resources/js/pages/`, see below.
- **plugins/** — the one place that calls `app.use(...)`. `app.ts` only
  calls `registerPlugins(app)`; adding a new global plugin later (analytics,
  error tracking, etc.) means editing `plugins/index.ts`, not `app.ts`.
- **services/** — thin, stateless wrappers around *infrastructure* concerns
  that outlive any one component and aren't tied to a business domain:
  `api.ts` (fetch client for *external* APIs — Laravel itself is called via
  Inertia visits/forms, not this), `upload.ts` (generic file upload with
  progress). No `ProductService`/`OrderService`/`AuthService` here — those
  belong in the owning module's own `services/`.
- **types/** — framework/global ambient declarations only: `global.d.ts`
  (Vite env, Inertia `PageProps`, Vue component custom properties) and
  `vue-shims.d.ts`. Everything with business or cross-cutting-but-generic
  meaning lives in a module's `types/` or `shared/types/` instead. The one
  necessary exception: `global.d.ts`'s `PageProps.auth` field imports `Auth`
  from `modules/auth/types/auth.ts`, since the Inertia shared `auth` prop
  needs a concrete type and `auth` is that type's owning module.

## Naming conventions

| What | Convention | Example |
|---|---|---|
| Composable | `useX.ts`, camelCase export matching filename | `useTheme.ts` → `useTheme()` |
| Store | `x.store.ts` inside a module, `x.ts` in `shared/stores/`; `defineStore('x', ...)`, exported as `useXStore` | `modules/auth/stores/auth.store.ts` → `useAuthStore`; `shared/stores/theme.ts` → `useThemeStore` |
| Service | `x.service.ts` inside a module, `x.ts` in global `services/`; exported as `xService` object or named functions | `modules/auth/services/auth.service.ts` → `authService` |
| Type/Interface | PascalCase, no `I`/`T` prefix | `ThemePreference`, `Toast` |
| Constant | `SCREAMING_SNAKE_CASE`, one concern per file | `HTTP_STATUS`, `STORAGE_KEYS` |
| Component file | PascalCase `.vue` | `Button.vue` |
| Directory | kebab-case | `shared/components/feedback/`, `modules/landing-pages/` |

## Pages: the one deliberate exception

Inertia resolves page components from the exact string passed to
`Inertia::render()`, and `app.blade.php`/`app.ts` both hardcode the page
root as `resources/js/pages/`. Existing Breeze auth/settings pages
(`pages/auth/`, `pages/settings/profile/`) stay exactly where they are —
don't move them into `modules/` pending a resolver change. For a *new*
domain feature's pages: keep a thin composition-root file under
`resources/js/pages/<domain>/` (the real Inertia entry point, wiring +
layout only) that imports its actual implementation from
`modules/<domain>/pages/` — that keeps business logic inside the module
while satisfying Inertia's path requirement.

## What's deliberately not here yet

- No `pinia`/`vue-i18n` business stores or locales beyond `en` — added when
  the first feature needs them.
- No code inside 15 of the 16 `resources/js/modules/<domain>/` directories
  — the folders and their full subfolder skeleton exist (tracked via
  `.gitkeep`), but no PRD domain module (product catalog, orders, CRM,
  etc.) has landed yet. Only `auth` has real content.
- No REST API layer — this app follows `Inertia::render()` /
  `Route::inertia()` per `CLAUDE.md`; `services/api.ts` is only for calling
  external, non-Laravel APIs.

## Vue component style guide

We follow the official [Vue.js Style Guide](https://vuejs.org/style-guide/),
adapted to this codebase's stack (`<script setup>` + TypeScript +
Composition API + Tailwind). Apply these by default when writing or reviewing
any `.vue` file. Priority letters match the upstream guide (A = essential,
B = strongly recommended, C = recommended).

**A — Essential (never skip):**

- **Multi-word component names** for components we author (`ProductCard`, not
  `Card`) — avoids clashing with current/future HTML elements. *Exception:*
  vendored primitives in `shared/components/ui/` keep shadcn-vue's single-word
  names (`Button.vue`, `Card.vue`) by convention; that's a deliberate,
  bounded carve-out, not license to name your own components with one word.
- **Typed prop definitions** — declare props via `defineProps<{ ... }>()` with
  explicit TypeScript types (and `withDefaults` where needed), never an
  untyped array of names.
- **Keyed `v-for`** — always bind a stable, unique `:key` (never the array
  index when items can reorder/insert/delete).
- **Never `v-if` on the same element as `v-for`** — filter in a `computed`, or
  move the `v-if` to a wrapping `<template>`.

**B — Strongly recommended:**

- **One component per file**; filename in PascalCase (matches the Naming
  conventions table above).
- **Self-close** components with no slotted content: `<ProductCard />`.
- **PascalCase in templates** for components: `<ProductCard>`, not
  `<product-card>`.
- **Prop names**: declare in `camelCase`; bind in templates in `kebab-case`
  (`:max-price="..."`).
- **Base/singleton naming**: base primitives read `Base*`/`App*`/`V*`;
  components rendered once per page read `The*` (`TheNavbar`); a child tightly
  coupled to a parent carries the parent's name as prefix (`ProductList` →
  `ProductListItem`).
- **Component-name word order**: start general, end specific
  (`SearchInputClearButton`, not `ClearButtonSearchInput`).
- **Full words over abbreviations** in names (`ProductDescription`, not
  `ProdDesc`).
- **One attribute per line** when an element has multiple attributes.
- **Directive shorthands only**, used consistently: `:` (`v-bind`), `@`
  (`v-on`), `#` (`v-slot`).
- **Keep template expressions simple** — push anything beyond a basic
  expression into a `computed` or a module composable; split complex
  `computed`s into smaller ones.

**C — Recommended:**

- **Consistent SFC top-level order**: `<script setup>` first, then
  `<template>`, then `<style>` (we rarely need `<style>` given Tailwind).
- **Consistent element attribute order** (definition/list `v-` directives →
  `id`/`ref` → `class` → other bindings → events).

**Stack-specific notes** (where the upstream guide assumes Options API / plain
CSS):

- The guide's *component-scoped styling* rule is satisfied by Tailwind utility
  classes on the element — do not add global unscoped CSS. If a `<style>`
  block is ever unavoidable, it must be `scoped`.
- The Options-API *component-options order* rule doesn't apply; with
  `<script setup>` keep a consistent intra-`<script>` order instead: imports →
  `defineProps`/`defineEmits` → composables/stores → local `ref`/`reactive` →
  `computed` → functions → lifecycle hooks → `watch`.
- Prefer props-down / events-up and Pinia stores over implicit parent-child
  mutation (the guide's Priority-D cautions), consistent with the module
  architecture above.
